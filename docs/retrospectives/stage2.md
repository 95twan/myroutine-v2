# Stage 2 회고

> `v1.1.0` 시점의 회고다. 운영 VM에 대용량 시드를 넣고 측정해 병목을 고친 Stage 2(S2-1a Baseline, S2-2 커서 조건, S2-3 커넥션 풀·예약 작업 스레드, S2-5 재고 차감 비교)에서 처음 계획과 달라진 것, 측정이 틀린 가정을 바로잡은 것, 어려웠던 것을 적는다.

## 계획과 달라진 점과 이유

| 처음 계획 | 바꾼 결과 | 이유 | 근거 |
|---|---|---|---|
| S2-1~S2-7을 측정 결과에 따라 차례로 | 꼭 하는 셋(S2-2, S2-3, S2-5)만 하고 나머지는 서브로 옮기거나 하지 않음 | 직접 설명할 수 있는 개선에 집중했다. S2-6·S2-7은 물리 서버 한 대에서 이득을 보일 수 없었다 | [Stage 2 준비 4절](../03-roadmap/stage2-plan.md), [Stage 2에서 남긴 개선](../04-sub/stage2-leftovers.md) |
| S2-3은 플랫폼·가상 스레드 비교와 트랜잭션 범위 축소 | 커넥션 풀 크기와 예약 작업 스레드 수 | Baseline에서 커넥션 대기와 메일 작업이 다른 예약 작업을 막는 것이 보였다 | [Baseline](../perf/s2-1a-baseline.md) |
| 측정 중에는 메일을 끈다 | 보내지 않고 한 통에 3초를 기다리는 가짜 발송기 | 그냥 끄면 메일 작업이 0초에 끝나 예약 작업이 막히는 상황을 재현할 수 없다 | [S2-3](../perf/s2-3-pool-scheduling.md) |
| 체크아웃은 풀 10과 고른 크기로 두 번 | 스냅샷을 되돌린 뒤 풀 10·20·30에서 연달아 | 풀 10 측정에서 체크아웃만 커넥션이 한계로 나왔다 | [S2-3](../perf/s2-3-pool-scheduling.md) |
| 재고 비교의 Redis 방식은 원자 차감 + DB 비동기 확정 | Redis 선착순 게이트 + 같은 트랜잭션의 조건부 UPDATE | 비동기 확정은 체크아웃 흐름이 바뀌고 Redis와 DB를 맞추는 보정과 장애 복구가 필요하다 | [Stage 2 준비 8.1](../03-roadmap/stage2-plan.md) |
| 재고 비교의 비관적 락은 `FOR UPDATE`로 읽은 뒤 조건부 UPDATE | JPA `@Lock(PESSIMISTIC_WRITE)`로 읽고 엔티티 메서드로 차감 | 처음 형태는 실제로 쓰지 않는 코드라 "비관적 락을 쓰면 어떤가"에 답하지 못했다 | [S2-5](../perf/s2-5-stock-reservation.md) |

## 측정이 바로잡은 가정

| 가정 | 측정 결과 | 근거 |
|---|---|---|
| 상품 조회는 커넥션 10개가 한계다 | 커넥션은 평균 4.9개만 쓰였고 VM CPU가 8코어 중 약 7코어였다. Hikari의 순간값(15초마다 0과 160 사이를 오감)에서 계산한 추정이 틀렸다 | [S2-3](../perf/s2-3-pool-scheduling.md) |
| 커서 페이징이니 몇 번째 페이지든 같은 속도다 | OR로 쓴 커서 조건이 인덱스를 타지 못해 커서 앞의 행을 모두 읽었다. 개발 가이드는 행 값 비교였는데 로드맵 예시가 OR로 어긋나 있었다 | [S2-2](../perf/s2-2-cursor.md) |
| Redis 게이트는 인기 상품 몰림에서 크게 빠르다 | DB 재고 UPDATE는 1/10이 됐지만 응답 차이는 측정의 흔들림 안이었다. 응답 대부분은 1,000건이 커넥션 31개를 나눠 쓰는 대기였다 | [S2-5](../perf/s2-5-stock-reservation.md) |

## 어려웠던 점

| 어려웠던 점 | 내용 |
|---|---|
| 측정을 같은 상태에서 다시 시작하기 | 쓰기 측정은 주문과 재고를 바꿔서 VM 스냅샷으로 되돌려야 했다. 되돌리면 앱 버전, `.env`, `/tmp`의 결과, Prometheus 데이터까지 함께 돌아가, 배포와 측정용 설정을 다시 넣고 결과를 먼저 옮기는 순서를 절차에 적어야 했다 |
| 측정 데이터가 실제 메일을 보냄 | 체크아웃 측정이 만든 결제 대기 주문이 15분 뒤 만료되며 시드 회원의 가짜 주소로 Gmail 발송을 했다. 측정 뒤 15분 안에 앱을 멈추는 규칙을 두었다가, S2-3에서 가짜 발송기로 바꿨다 |
| 실행마다의 흔들림 | 같은 조건에서도 상품 조회 처리량이 13% 흔들렸다. 한 번씩 잰 차이(S2-2 상한 10의 p95 124 → 172ms)는 원인을 가리지 못했고, S2-3부터 같은 조건을 세 번씩 쟀다 |
| 몇 초짜리 측정 | 인기 상품 몰림은 3초 만에 끝나 15초 간격의 Prometheus로 볼 수 없었다. `pg_stat_statements`를 측정 직전에 비우고 문장별 평균 시간으로 락 대기를 봤다 |
| 원격 VM 측정의 자동화 | 부하는 개발 PC, 지표는 VM에서 모아야 해서, 두 곳의 스크립트를 같은 시작 시각에 맞춰 칸 단위로 돌렸다. 한 칸에서 1,000건 중 51건이 앱에 닿기 전에 끊겨 그 측정만 다시 쟀다 |

## 다시 한다면

| 다시 한다면 | 이유 |
|---|---|
| Baseline부터 같은 조건을 세 번 잰다 | 흔들림의 크기를 알아야 개선이 흔들림을 넘었는지 말할 수 있다 |
| 순간값 대신 평균 지표를 처음부터 쓴다 | 순간값 하나로 "커넥션이 한계"라고 판단했다가 S2-3에서 바로잡았다 |
| 원인을 확인할 지표를 측정 계획에 넣는다 | 체크아웃이 풀을 늘리자 빨라진 것을 group commit으로 설명했지만, 디스크 쓰기 횟수(`pg_stat_wal`)를 재지 않아 확인하지 못했다 |
| 비교할 대안은 실제로 쓰는 형태로 정한다 | 변수를 줄이려고 만든 비관적 락 형태를 측정 직전에 다시 구현했다 |
