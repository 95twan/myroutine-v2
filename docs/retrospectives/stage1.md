# Stage 1 회고

> `v1.0.0` 시점의 회고다. 모듈러 모놀리스(Part 1~6)를 만들면서 처음 설계와 달라진 것, 리뷰에서 반복된 것, 어려웠던 것을 적는다.

## 설계와 달라진 점과 이유

| 처음 설계 | 바꾼 결과 | 이유 | 근거 |
|---|---|---|---|
| 예치금과 Toss 복합결제 | Toss 단일 결제. 환불은 PG 부분취소, 정산금은 지급 Mock | 재고 예약, 결제 대사, 누적 취소 한도, 정산 1회처럼 정합성을 다루는 사례가 예치금 없이도 남고, 결제 경로가 하나로 줄어든다. 예치금 동시 차감과 원장 대조 사례는 잃었다 | [ADR-005](../adr/ADR-005-wallet-ledger.md) |
| 주문번호, 바로 구매, PG 호출 로그 테이블, 대사 백오프 등을 처음부터 구현 | 추가 항목으로 빼고 핵심 경로만 구현 | 아직 쓰는 곳이 없거나 지금 규모에 과했다. 만들면 구현과 리뷰 비용만 늘어난다 | [Part 2 버전 0.5](../03-roadmap/part2-order-money.md) |
| 구독, 취향 추천, 월간 리뷰 요약, 무중단 재색인을 로드맵에 포함. k3s 전환은 Stage 2 앞에 고정 | 모두 서브로 옮겼다 | 주문·결제 핵심 경로를 먼저 끝내려고 범위를 줄였다. 대신 Stage 2 Baseline을 compose VM에서 재면 k3s로 옮긴 뒤 다시 재야 한다 | [로드맵 버전 0.20~0.23](../03-roadmap/README.md), [ADR-012](../adr/ADR-012-kubernetes-zero-downtime.md) |
| 가입 후 이메일 인증, 서버에 저장한 OAuth `state`, 세션의 기기 정보 | 가입 전 인증, 프론트가 비교하는 `state`, 기기 정보 삭제 | 미인증 회원 상태를 없애면 인증 클레임과 검사가 필요 없다. 서버 저장 `state`는 브라우저와 묶이지 않아 로그인 CSRF를 막지 못한다. 기기 목록은 쓰는 기능이 없다 | [Part 4 버전 0.31·0.33·0.34](../03-roadmap/part4-auth.md) |
| 체크아웃 때 장바구니 정리 | 결제 완료 때 주문 수량만큼 차감 | 실패와 만료에서 장바구니를 되돌릴 일이 없고, 주문과 장바구니를 연결해 둘 필요가 없다 | [Part 2 버전 0.12](../03-roadmap/part2-order-money.md) |
| PG 취소 반영과 발송의 경합을 `@Version`으로 처리 | `payment` 행 잠금, 발송의 주문 행 잠금 | 서로 다른 품목의 동시 취소가 정상 요청인데 409가 됐고, 취소와 발송이 겹치면 환불이 `PG_CANCELLED`에 멈췄다 | [Part 2 버전 0.83·0.84](../03-roadmap/part2-order-money.md) |
| 로그인 잠금과 인증 코드 횟수를 앱에서 읽고 비교한 뒤 기록 | Redis Lua 스크립트로 한 번에 처리 | 동시에 보낸 요청이 모두 검사를 통과해 횟수 제한을 넘었다 | [Part 4 버전 0.40·0.46](../03-roadmap/part4-auth.md) |
| 검색 문서에 표시 값을 모두 저장 | ES는 순서만 정하고 표시 값은 상품 DB에서 읽음 | 사진과 재고는 이벤트를 내지 않는 쓰기 경로가 바꾼다. 문서에 넣으면 재고 핫스팟 경로에 발행이 늘어난다 | [ADR-013](../adr/ADR-013-search-hydration.md) |
| 관측 스택은 로컬에서만 실행 | 운영 VM에도 올림 | 배포한 앱을 로그와 메트릭으로 보는 것까지가 운영 연습이고, Stage 2 전후 비교의 이력도 VM에 남아야 한다 | [ADR-011 9항](../adr/ADR-011-ops-practice-environment.md), [Part 6 버전 0.36](../03-roadmap/part6-ops-wrapup.md) |
| PG가 거절한 환불은 재시도만 가능 | `FAILED`를 진행 중인 환불로 보고 관리자 종결 API를 더함 | `FAILED` 환불이 있는 품목을 발송하거나 다시 취소할 수 있었고, 재시도해도 안 되는 환불을 닫을 방법이 없었다 | [Part 6 버전 0.39](../03-roadmap/part6-ops-wrapup.md) |

## 리뷰에서 반복된 지적

| 유형 | 반복된 사례 | 이후 바꾼 것 |
|---|---|---|
| 확인과 쓰기 사이의 틈 | 로그인 잠금과 토큰 버전 캐시(4-4). 같은 유형이 멱등 키 만료와 인증 코드 횟수에서도 나왔다 | 원자적 SQL·Lua와 동시성 테스트 |

## 어려웠던 점

| 어려웠던 점 | 내용 |
|---|---|
| 상태 조합 | 주문, 가게주문, 품목, 환불, 결제가 함께 움직여 한 전이의 영향이 여러 곳에 번졌다. 2-8과 2-9에서 규격이 가장 많이 바뀌었고, 2-9 도중에 [상태 조합 문서](../02-design/10-state-combinations.md)를 따로 만들어 정리했다 |
| 잠금의 기준 | 잠금이 있는 상태에서 테스트가 통과해도 잠금의 증거가 아니었다. 2-9를 지나며 "서로 다른 행을 바꾸며 서로의 결과를 읽는 작업이면 행 잠금, 같은 행이면 `@Version`"이라는 기준을 얻었다 |
| 결과를 모르는 외부 호출 | PG 응답이 성공, 실패, 모름 셋이라 경로가 늘었다. 승인 뒤 반영 실패의 보상 취소까지 포함하면 대사의 분기가 많아졌고, [알려진 한계](../known-issues.md)도 여기에 몰려 있다 |
| 비동기 테스트의 타이밍 | 스케줄러가 테스트 중에 돌아 간헐적으로 실패했고(2-10), 이벤트 테스트가 끝 신호가 아닌 첫 항목을 기다렸다(3-4). Kafka 재시도 대기가 쌓여 CI가 5분에서 9분까지 늘었다 |
| 처음 쓰는 기술과 최신 버전 | nori 품사 필터가 `마스크팩`의 일부를 버려 검색되지 않았고, 로그 인덱스 이름 `logs-*`는 ES 기본 템플릿과 충돌했다. 컨트롤러의 `@Validated`가 검증 예외를 바꿔 400이 500이 됐고, Modulith가 스케줄링을 켜 두어 테스트 설정을 하나 더 찾아야 했다 |
| 운영 실패의 재현 | 자동 롤백을 확인하려면 배포를 일부러 실패시켜야 했는데, 기동을 확실히 실패시키는 설정을 찾기까지 임시 PR을 세 번 올렸다(#17~#19) |
