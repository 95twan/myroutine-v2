# ADR-001. 모듈러 모놀리스로 시작하고 측정 기반으로 MSA까지 진화한다

- 상태: 승인 (2026-10-02)
- 관련: [01-architecture-evolution.md](../02-design/01-architecture-evolution.md), [00-as-is](../00-as-is/README.md)

## 맥락
- 원 팀 프로젝트는 처음부터 MSA(서비스 8개 + Gateway·Eureka·Config)로 시작했다. 결과를 보면:
  - 서비스 간 정합성 결함이 핵심 흐름에 집중됐다 (ORD-02 원격 호출 후 커밋 실패, ORD-10, WAL-01 등).
  - 테스트는 사실상 0개가 실행됐고(INF-01), 관측성은 없었다(INF-02). 운영 인프라를 유지하느라 품질에 쓸 시간이 부족했다.
  - Feign 순환 의존(INF-04), schema 침범(BAT-03)으로 경계도 실제로는 지켜지지 않았다.
- v2는 1인 개발이다. 서비스 수만큼 배포·관측·장애 지점이 늘어나는 비용을 감당하기 어렵다.

## 결정
1. Stage 1은 **모듈러 모놀리스**로 만든다. 모듈 경계는 Spring Modulith 테스트로 강제한다.
2. Stage 2에서 부하 테스트로 병목을 측정하고 튜닝 → 캐시 → 레플리카 → 파티셔닝 → (실험) 샤딩 순으로 개선한다.
3. Stage 3에서 **성능이 아닌** 확장 특성 차이·장애 격리·배포 독립성을 근거로 Strangler Fig 방식으로 MSA로 전환한다.

## 고려한 대안
| 대안 | 기각 이유 |
|---|---|
| 원 프로젝트처럼 처음부터 MSA | 결함의 원인이 된 구조. 1인 개발에서 운영 비용이 품질을 잠식 |
| 경계 없는 일반 모놀리스 | Stage 3 전환이 사실상 재작성이 됨. 모듈 경계를 증명할 수 없음 |
| 서비스 3~4개 축소 MSA | 분산 트랜잭션 경험은 얻지만, 측정 기반 진화라는 서사를 잃고 Stage 2(DB 확장) 실험이 서비스 간 노이즈에 가려짐 |

## 결과
- 장점: 체크아웃을 로컬 트랜잭션으로 원자 처리할 수 있다. 테스트·디버깅·성능 측정이 단순하다. MSA 전환 시 "무엇이 왜 어려워지는지"를 직접 비교할 수 있다.
- 단점: 모듈 경계가 테스트로만 강제된다. 하나의 장애(커넥션 고갈 등)가 전체에 번질 수 있다 → Stage 3의 근거로 측정한다.
- 남은 분산 문제: 외부 PG·은행·메일·OpenAI 연동, Kafka 비동기 처리는 모놀리스에서도 그대로 존재한다 (ADR-004).

## 면접 연결
- "왜 MSA를 적용했나요?" → 원 프로젝트에서 적용했던 이유와 실제 비용을 수치로 설명하고, v2에서 모놀리스로 시작한 근거를 제시
- "MSA의 단점은 무엇이었고 어떻게 대응했나요?" → 결함 목록(00-as-is/04-issues.md)과 Stage 3의 전환 기준
