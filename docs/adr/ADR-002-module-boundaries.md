# ADR-002. 모듈 경계와 모듈 간 통신 규칙

- 상태: 승인 (2026-10-02)
- 관련: [02-architecture-stage1.md §3](../02-design/02-architecture-stage1.md)

## 맥락
모놀리스에서 경계가 무너지는 전형적인 경로는 다른 모듈의 엔티티·리포지토리를 직접 쓰거나, 테이블을 조인하거나, 순환 의존이 생기는 것이다. Stage 3에서 서비스로 떼어낼 때 이것들이 모두 재작성 비용이 된다.

## 결정
1. **공개 표면**: 다른 모듈은 `{module}.api` 패키지(인터페이스 + DTO + 이벤트 타입)만 참조한다.
2. **동기 호출**: 정해진 방향(order→product/payment/shop/member, member→shop(조회), settlement→shop(가게 주인 조회), notification→member/shop(수신자 조회), product→shop, review→order, recommendation→product, search→product(재색인용 목록))만 허용하고 순환은 금지한다. (2026-10-02 개정: settlement·notification의 조회 의존 추가, 예치금 제거로 wallet 관련 방향 삭제)
3. **트랜잭션**: 한 요청 안의 모듈 간 동기 쓰기는 하나의 로컬 트랜잭션으로 묶을 수 있다. 외부 시스템 호출은 트랜잭션 밖에서 한다.
4. **멱등 API**: 모듈 API의 쓰기 메서드는 비즈니스 키(orderId, refundId, settlementId)를 받고, 같은 키로 다시 호출해도 결과가 같다. Stage 3에서 원격 호출 + 재시도로 바꿔도 의미가 유지된다.
5. **역방향 통지는 이벤트**로 한다 (예: product의 가격 변경 → order 구독).
6. **역방향 조회가 꼭 필요하면 의존을 역전**한다. 예: 가게 폐업 조건(진행 중 주문)은 shop이 `ShopClosePrecondition`을 정의하고 order가 구현한다.
7. **데이터**: 모듈마다 schema를 소유한다. 다른 schema를 조회·조인하지 않고, 다른 모듈 엔티티를 ID 값으로만 참조한다.
8. 1·2는 Spring Modulith `ApplicationModules.verify()` 테스트로 CI에서 검증하고, 7(schema 침범)은 코드 리뷰로 확인한다.

## 고려한 대안
| 대안 | 기각 이유 |
|---|---|
| 모든 모듈 간 통신을 이벤트로 | 체크아웃처럼 즉시 일관성이 필요한 흐름까지 최종적 일관성이 되어, 모놀리스의 장점을 버리고 복잡도만 늘어남 |
| 모듈 간 쓰기도 각자 트랜잭션 (Stage 1부터 Saga) | Stage 3에서 할 일을 미리 하는 것. Saga 전환 과정 자체가 Stage 3의 학습·이력서 포인트 |
| 경계 강제 없이 패키지 규칙만 | 시간이 지나면 반드시 깨짐. 원 프로젝트에서도 schema 침범이 발생 |

## 결과
- Stage 3 분리 시 바꿀 부분이 "모듈 API 구현체를 HTTP 클라이언트로 교체 + 로컬 트랜잭션을 Saga로 교체"로 한정된다.
- 로컬 트랜잭션에 기대는 흐름 목록(체크아웃, 환불 완료, 정산 지급)을 미리 관리하고, Stage 3에서 이것이 Saga 설계 대상이 된다.

## 면접 연결
- "서비스 분리 기준은 무엇이었나요?" → 모듈 = 데이터 소유 단위 + 변경 이유 단위, 동기 의존 그래프
- "모놀리스에서 MSA로 바꿀 때 무엇이 어려웠나요?" → 로컬 트랜잭션 의존 흐름 목록이 곧 답
