# ADR-004. 체크아웃·결제 정합성: 주문 상태로 경합을 차단하고, 불확실한 PG 결과는 대사로 확정한다

- 상태: 승인 (2026-10-02)
- 관련: [04-state-machines.md §1, §5](../02-design/04-state-machines.md), [06-sequences.md §1~3](../02-design/06-sequences.md), INV-01·02·04

## 맥락
- As-Is 결함: 클라이언트 가격 신뢰(ORD-01), 트랜잭션 안의 원격 호출(ORD-02), PG 타임아웃을 실패로 단정(PAY-01), 중복 승인(PAY-02), 불확실한 출금 결과(ORD-10).
- Toss는 결제창에서 **인증**만 하고, **승인은 가맹점 서버가 confirm API를 호출할 때** 일어난다. 인증 후 승인되지 않은 건은 PG 측에서 소멸한다.
- 외부 PG 호출은 네트워크를 지나므로 응답이 성공·실패·**모름** 세 가지다.

## 결정
1. **가격은 서버가 확정**한다. 체크아웃 요청에는 상품 ID와 수량만 받는다.
2. **체크아웃은 하나의 로컬 트랜잭션**으로 처리한다: 주문(PENDING_PAYMENT, 15분 만료) + 재고 예약. (2026-10-02: 예치금 제거로 보류 단계 삭제, 결제는 Toss 단일 수단)
3. **승인 시작은 CAS 전이**(`PENDING_PAYMENT → PAYMENT_IN_PROGRESS`)로 한다. 실패하면(만료·중복) PG를 호출하지 않는다. 만료 스윕은 `PENDING_PAYMENT`만 대상으로 한다 → "만료된 주문 + 승인된 결제" 조합이 생길 수 없다.
4. **PG 호출 전에 payment(IN_PROGRESS)를 먼저 커밋**한다. 앱이 호출 도중 죽어도 대사 대상이 남는다.
5. PG 응답 분류: 승인 → 같은 트랜잭션에서 주문 완료. 명확한 거절(4xx, 거절 코드) → 실패 + 예약 해제. **타임아웃·5xx·네트워크 오류 → UNKNOWN**, 주문은 PAYMENT_IN_PROGRESS로 유지.
6. **대사는 주문 모듈이 주도**한다. 주문 대사 잡이 PAYMENT_IN_PROGRESS 주문을 찾아 `PaymentApi.reconcile(orderId)`로 결과를 묻고(payment가 PG 조회 API로 확정), 받은 결과로 주문을 완료하거나 실패 처리한다. 승인됐는데 주문을 완료할 수 없으면 PG 승인을 취소한다(보상). 이벤트를 쓰지 않으므로 Kafka 없이 동작하고, 흐름의 책임자가 주문 하나로 분명하다.
7. **멱등성 3중 방어**: API `Idempotency-Key` / `payment(purpose, reference_id)` unique / PG 호출 `Idempotency-Key`.

## 고려한 대안
| 대안 | 기각 이유 |
|---|---|
| 타임아웃이면 실패 처리 후 사용자 재시도 | 승인됐으면 이중 결제 또는 돈만 빠짐 (As-Is PAY-01) |
| 타임아웃이면 즉시 PG 취소 | 취소 호출도 불확실할 수 있고, 실제로 실패한 건에 대한 취소는 불필요. 조회로 사실을 확정하는 쪽이 정확 |
| 분산 락(Redis)으로 승인·만료 경합 제어 | DB 상태 CAS로 충분하고, 락 만료·장애라는 새 실패 지점이 생김 |
| 결제를 먼저 받고 재고를 나중에 차감 | 재고 부족 시 환불이 일상적으로 발생, 사용자 경험 나쁨 |

## 결과
- INV-02(승인 1건은 정확히 1회 반영, 반영 못 하면 취소)를 상태머신 + 대사로 보장한다.
- 사용자는 드물게 "결제 확인 중(202)" 상태를 본다. 클라이언트는 주문 상태를 폴링한다.
- 재고가 대사가 끝날 때까지(최대 수 분) 묶일 수 있다. 메트릭 `payment_unknown_total`과 최장 대기 시간을 알림 대상으로 둔다.
- 테스트: 테스트용 가짜 PG 서버(JDK 내장 HttpServer)로 지연·타임아웃·5xx·4xx를 주입하는 시나리오 테스트 (NFR-TST-04).
- Stage 3에서는 2번의 로컬 트랜잭션이 Saga가 되면서, product 자체 예약 TTL이 추가로 필요해진다.

## 면접 연결
- "외부 결제 API가 타임아웃 나면 어떻게 하나요?" — 이 ADR의 핵심
- "2PC를 쓰지 않은 이유는?" → 외부 PG는 2PC 참여자가 될 수 없음. 상태머신 + 멱등 + 대사가 현실적인 해법
- "중복 결제는 어떻게 막았나요?" → 멱등성 3중 방어
