# ADR-008. 재고: 조건부 UPDATE + 예약 레코드 + 수량 4분할, 대안은 Stage 2에서 측정 비교

- 상태: 승인 (2026-10-02), S2-5 측정 뒤 유지 (2026-11-07)
- 관련: [03-erd.md product](../02-design/03-erd.md), INV-03·04, NFR-PERF-03

## 맥락
- As-Is의 장점: `UPDATE stock SET quantity = quantity - :q WHERE quantity >= :q` 원자 차감과 예약 CAS 전이, 동시성 테스트(As-Is catalog-service, 팀원 구현).
- As-Is의 문제: 예약 만료 없음(CAT-01), 판매자 재고 수정이 절대값 덮어쓰기(CAT-06), 복구 이력 추적 불가.

## 결정
1. `stock(available, reserved, sold, received)` 4개 수량으로 관리한다. 모든 전이는 조건부 UPDATE 한 문장이다. 불변식은 `available + reserved + sold = received`.
2. 예약은 `stock_reservation(order_id, product_id UK)` 레코드다. 만료는 주문 모듈의 만료 스윕이 주도한다(ADR-004).
3. 판매자 재고 변경은 **증감량(delta)**으로만 받는다: `available += delta, received += delta` (`available + delta >= 0` 조건).
4. 모든 수량 변화는 `stock_movement`에 기록하고, unique 제약으로 예약·복구의 멱등을 보장한다.
5. 여러 상품 예약 시 **상품 ID 오름차순으로 UPDATE**해 교차 주문 간 데드락을 막는다.

## Stage 2에서 비교할 대안 (S2-5 핫스팟 실험)
| 방식 | 예상 특성 |
|---|---|
| A. 조건부 UPDATE (현 결정) | 단순, 정확. 인기상품 행에 락 대기 집중 |
| B. `SELECT FOR UPDATE` 후 차감 | A보다 락 보유 시간이 김. 기준선으로 측정 |
| C. Redis 원자 차감(Lua) + DB 비동기 확정 | 처리량 최고. Redis-DB 불일치 보정과 장애 시 복구가 필요 |
| D. 재고 버킷 분할(행 N개로 쪼갬) | 경합 분산. 잔여 수량이 적을 때 처리가 복잡 |

측정: 재고 100에 동시 1,000건 → 성공 정확히 100건, TPS, p95, DB 락 대기 시간. 결과에 따라 이 ADR을 갱신한다(supersede).

## S2-5 측정 결과

A·B·C를 커넥션 풀 31에서 몰림(재고 100에 1,000명)과 지속 경합(재고 100만에 100명, 3분)으로 3번씩 쟀다([리포트](../perf/s2-5-stock-reservation.md)). B는 JPA `@Lock(PESSIMISTIC_WRITE)`, C는 Lua로 Redis 수량을 먼저 확인·차감한 뒤 통과한 요청만 A의 UPDATE를 하는 선착순 게이트로 구현했다. D는 재지 않았다.

| 방식 | 초과 판매 | 지속 경합 처리량 / p95 | 몰림 p95 |
|---|---|---|---|
| A | 0 | 초당 268\~293건 / 628\~686ms | 907\~1,162ms |
| B | 0 | 초당 261\~279건 / 892\~960ms | 985\~1,212ms |
| C | 0 | 초당 276\~293건 / 616\~661ms | 896\~921ms |

- 처리량은 세 방식 모두 재고 행 하나가 정했다(초당 약 290건, 커넥션 대부분이 행 락 대기, CPU 1코어 미만).
- B는 처리량이 같고, 가장 느린 1% 응답(p99)과 최대 응답이 A의 2\~3배였다.
- C는 거절 900건을 Redis에서 끝내 DB 재고 UPDATE를 1/10로 줄였지만, 응답 차이는 A의 흔들림 범위 안이었다. 운영에 넣으려면 재고가 바뀌는 모든 경로에서 Redis를 맞추고 어긋남을 보정해야 한다.

결정 1(조건부 UPDATE)을 유지한다. C는 재고 수량을 Redis와 DB 두 곳에 두게 되어, 재고가 바뀌는 모든 경로(등록·판매자 변경·예약 해제·재고 복구)에서 Redis를 맞추고, 앱 장애로 어긋난 값을 보정하고, Redis 장애 때 DB로 넘기는 일이 필요하다. 초과 판매는 C에서도 DB 조건이 막으므로 이 비용은 정확성이 아니라 두 값을 맞추기 위한 것인데, 측정에서 얻는 이득이 응답 차이로 드러나지 않았다.

다시 검토할 때: 재고보다 훨씬 많은 요청이 몰려 거절 요청이 커넥션과 DB를 차지하는 것이 측정으로 보이면 C의 게이트를, 재고 행 하나의 처리량 한계(초당 약 290건)를 넘어야 하면 D나 C의 비동기 확정을 본다.
