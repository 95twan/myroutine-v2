# ADR-015. 인증: DB 세션 + 헤더의 세션 토큰

- 상태: 승인 (2026-11-22). [ADR-006](ADR-006-auth.md)의 결정 1·3·4(JWT, tokenVersion, refresh 회전)를 대체한다. 결정 2(판매자 기능은 소유권으로 인가)와 5(관리자 경로는 ADMIN 역할)는 그대로다.
- 관련: [서브 SUB-25](../04-sub/session-auth.md), [서브 Redis 장애 대응](../04-sub/redis-outage.md), FR-MEM-03·04, NFR-PERF-04

## 맥락
- ADR-006은 역할을 담은 access JWT(15분)를 쓰면서, 제재·탈퇴·전체 로그아웃을 바로 반영하려고 인증 필터가 요청마다 Redis의 `tokenVersion`을 토큰 값과 비교하게 했다. 요청마다 저장소를 조회하므로 access 검증은 무상태가 아니다.
- 서명만으로 신원을 확인하는 JWT는 두 조건이 함께 맞을 때 쓰는 도구다. 발급자와 검증자가 다르고(외부 인증 서버, 다른 회사가 발급한 토큰, 인증 서버와 분리된 서비스), 검증자가 요청마다 발급자나 저장소에 묻지 않고 서명만으로 받아들인다(차단은 짧은 만료로 늦게 반영된다). 검증자가 요청마다 묻는다면 발급자와 검증자가 달라도 아무 정보도 담지 않은 무작위 토큰을 인증 서버에 확인하는 것(OAuth 토큰 조회)과 같다. 이 앱은 같은 서버가 발급하고 검증하며, 요청마다 Redis에 묻는다. JWT를 고른 근거였던 서비스 분리(Stage 3)도 요청마다 `tokenVersion`을 조회하는 한 성립하지 않는다. 게이트웨이가 요청마다 Redis를 보는 것은 세션과 같다.
- 요청마다 하는 조회를 빼면 JWT의 이점은 살지만 얻는 것은 저장소 조회 한 번이고, 대가는 제재·비밀번호 변경이 access 만료(15분)까지 반영되지 않는 것이다. 비밀번호 변경은 계정을 탈취당했을 때 하는 조치라 이 지연을 받아들이지 않는다.
- 그래서 JWT는 세션과 같은 일을 하면서 tokenVersion, refresh 회전, 재사용 탐지, access/refresh 두 토큰을 더 짊어진다. Redis 장애 대응([서브 SUB-24~](../04-sub/redis-outage.md))을 설계하면서 이 장치들 때문에 장애 중 버전 대체 읽기, 세션의 토큰 버전, 커밋 뒤 세션 삭제 같은 단계가 셋 더 필요해졌다.

## 결정
1. 로그인·가입·소셜 로그인은 세션을 하나 만들고 세션 토큰을 응답 본문으로 준다. 세션 토큰은 무작위 32바이트를 base64url로 쓴 문자열이라 JWT와 달리 안에 회원 정보가 없고, 서버가 DB에서 찾아봐야 누구인지 안다. 클라이언트는 `Authorization: Bearer {token}`으로 보낸다. 쿠키를 쓰지 않으므로 CSRF 대응이 필요 없다.
2. 세션은 DB `member.auth_session`에만 둔다. 토큰 원문은 저장하지 않고 SHA-256 해시로 찾는다. Redis는 쓰지 않는다.
3. 인증 필터는 요청마다 토큰 해시로 세션과 회원을 함께 읽는다. 세션이 만료됐거나 회원이 `ACTIVE`가 아니면 인증하지 않는다. 역할은 세션에 저장하지 않고 회원 행에서 읽으므로 SELLER·ADMIN 변경이 다음 요청부터 반영된다.
4. 세션은 마지막 사용 뒤 7일이 지나면 만료된다. 쓸 때마다 만료를 미루되, DB 쓰기를 줄이려고 마지막 연장 뒤 하루가 지났을 때만 `UPDATE`한다.
5. 로그아웃·전체 로그아웃·비밀번호 변경·재설정·제재·탈퇴는 세션 행을 같은 트랜잭션에서 지운다. 커밋이 곧 무효화다.
6. 만료된 세션 행은 매일 정리 작업이 지운다.

## 고려한 대안
| 대안 | 기각 이유 |
|---|---|
| JWT 유지(ADR-006) | 맥락과 같다. 요청마다 Redis를 조회해 세션과 같은 일을 하면서 장치가 더 많다 |
| 무상태 JWT(요청마다 조회 없이 refresh 때만 확인) | 비밀번호 변경·제재가 access 만료(15분)까지 반영되지 않는다. 얻는 것은 요청마다 조회 한 번이다 |
| 세션을 Redis에만 둔다 | 얻는 것: 키 만료(TTL)가 세션 만료를 맡아 정리 작업이 없고, 만료 연장도 요청마다 `EXPIRE` 한 번이면 되며, 요청마다의 조회가 DB와 커넥션 풀(31)을 쓰지 않는다. 고르지 않은 이유: Redis가 멈추면 로그인한 요청이 모두 실패하는데, 이 앱은 Redis 장애 중에도 로그인한 요청을 진행한다([서브 Redis 장애 대응](../04-sub/redis-outage.md) 정책). 또 회원 상태·역할은 DB에 있어, 요청마다 확인하려면 결국 DB를 읽거나 세션에 복사해 두고 바뀔 때마다 맞춰야 한다 |
| DB 세션 + Redis 캐시 | 얻는 것: 요청마다의 조회가 대부분 Redis에서 끝나 DB 부하가 준다. 고르지 않은 이유: 세션을 지운 뒤 캐시 삭제가 실패하거나 동시에 들어온 요청이 옛 값을 다시 채우면 지운 세션이 캐시에 남아 통과한다. 막으려면 짧은 캐시 만료(그동안은 통과)나 별도 장치가 필요하다. 캐시가 필요한지는 재지 않았다(SUB-16에서 인증 비용을 잰다) |
| HttpOnly 쿠키로 세션 ID 전달 | JS가 토큰을 읽지 못해 XSS 탈취를 막지만, CSRF 대응과 프론트·API 도메인이 다를 때의 CORS credentials 설정이 필요하다. 헤더 방식은 지금 프론트·테스트 흐름과 같다 |
| Spring Session | 새 라이브러리다. 필요한 것은 테이블 하나와 필터 하나라 직접 만든다 |

## 결과
- 로그인한 요청마다 DB 조회 1번(세션과 회원을 기본키·유니크 인덱스로 조인), 세션당 하루 최대 1번 `UPDATE`가 생기고, 그때마다 커넥션 풀(31)의 연결을 잠깐 쓴다. 만료된 행은 정리 작업이 지운다. Redis 조회는 없어진다. 비용은 [서브 SUB-16](../04-sub/stage2-leftovers.md)의 S-04로 JWT 때와 비교해 잰다(NFR-PERF-04). 기준(헤더 있음과 없음의 p95 차이 10ms 미만)을 넘거나 커넥션 풀 대기가 생기면 Redis 캐시를 더한다.
- Redis 장애는 로그인한 요청과 로그아웃·비밀번호 변경·제재·탈퇴에 영향을 주지 않는다. Redis는 로그인 실패 횟수, 이메일 인증 코드, 가입 인증·소셜 가입 토큰에만 남는다.
- tokenVersion, refresh 토큰과 `/api/auth/refresh`, `REFRESH_REUSED`, JWT 서명 키(`JWT_SECRET`)가 없어진다. `member.token_version` 컬럼은 롤백할 수 있게 남겼다가 다음 배포에서 지운다([ADR-011](ADR-011-ops-practice-environment.md) 결정 7). 배포하면 모든 사용자가 한 번 다시 로그인한다.
- 토큰을 JS가 들고 있으므로 XSS로 탈취될 수 있는 점은 JWT 때와 같다. 탈취된 토큰은 비밀번호 변경이나 전체 로그아웃으로 바로 끊을 수 있다.

## 면접 연결
- "왜 JWT에서 세션으로 바꿨나요?" → 맥락: 즉시 차단을 위해 요청마다 저장소를 보면서 JWT의 이점이 사라졌고, 발급자와 검증자가 같은 구조라 세션이 맞았다
- "세션의 단점은?" → 요청마다 저장소 조회와 그 저장소에 대한 의존. CSRF·도메인 문제는 쿠키 문제라 헤더로 보내 피했다
- "JWT는 언제 쓰나요?" → 발급자와 검증자가 다르고(OIDC ID 토큰, 외부 인증 서버, 서비스 간 신원) 검증자가 묻지 않고 서명만으로 받아들일 때. 차단은 짧은 만료로 늦게 반영되는 것을 받아들인다
