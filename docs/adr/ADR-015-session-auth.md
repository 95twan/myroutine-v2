# ADR-015. 인증: 세션은 DB에, JWT access는 세션을 가리키는 토큰으로

- 상태: 승인 (2026-11-24). [ADR-006](ADR-006-auth.md)의 결정 1(access의 `role`·`tokenVersion` 클레임), 3(tokenVersion 즉시 무효화), 4(Redis의 refresh 세션)를 바꾼다. access JWT 15분, refresh 회전과 재사용 탐지, 결정 2(판매자 기능은 소유권으로 인가)와 5(관리자 경로는 ADMIN 역할)는 그대로다.
- 관련: [서브 SUB-25](../04-sub/session-auth.md), [서브 Redis 장애 대응](../04-sub/redis-outage.md), FR-MEM-03·04, NFR-PERF-04

## 맥락
- ADR-006은 제재·탈퇴·전체 로그아웃을 바로 반영하려고 인증 필터가 요청마다 Redis의 회원 단위 `tokenVersion`을 access의 값과 비교했다. refresh 세션도 Redis에만 있었다.
- 그래서 Redis가 멈추면 로그인한 요청, 갱신, 로그아웃이 모두 실패했다. Redis 장애 대응을 설계하자 버전 대체 읽기, 세션의 토큰 버전, 커밋 뒤 세션 삭제 같은 장치가 셋 더 필요해졌다.
- 끊기는 회원 단위 버전이라, 한 기기만 로그아웃하거나 refresh 재사용으로 세션을 지워도 그 기기의 access는 만료(15분)까지 통했다. 역할도 access 클레임이라 다음 갱신 때 반영됐다.
- 재사용 탐지는 유지한다. 탐지하려면 토큰을 회전해야 하는데, 요청마다 쓰는 토큰을 회전하면 그 순간 이미 출발한 요청이 옛 토큰을 들고 와서 직전 값과 유예 시간을 저장해야 한다. 그래서 회전하는 refresh와 회전하지 않는 access를 나눈다.
- access에는 짧은 만료가 있어야 한다. 없으면 access만 훔쳐도 refresh 없이 계속 쓸 수 있어 재사용 탐지가 아무것도 잡지 못한다. 그 만료를 저장하지 않으려면 토큰 안에 위조할 수 없게 담아야 하므로 서명된 토큰이 필요하다. 그 표준이 JWT이고 이미 jjwt로 쓰고 있어 그대로 둔다. 서명 문자열을 직접 만들어도 되지만 JWT를 다시 만드는 셈이다.

## 결정
1. access JWT(15분)는 `sub`(회원 ID)와 `sid`(세션 ID)만 담는다. 회전하지 않고 저장하지 않는다.
2. refresh(7일, `{sid}.{비밀값}`)는 지금처럼 쓸 때마다 회전하고, 저장된 해시와 다르면 재사용으로 보고 세션을 지운다. 회전은 "해시가 같을 때만" 조건부 `UPDATE`다. 절대 만료는 두지 않는다.
3. 세션은 DB `member.auth_session`(refresh 해시, 만료)에만 둔다. Redis는 쓰지 않는다.
4. 인증 필터는 서명·만료를 확인한 뒤 요청마다 DB에서 `sid`의 세션이 만료 전이고 회원이 `ACTIVE`인지 확인하고, 역할도 회원 행에서 읽는다.
5. 끊기는 세션 행 삭제다. 로그아웃·전체 로그아웃·비밀번호 변경·재설정·제재·탈퇴는 같은 트랜잭션에서 지우고, 그 세션의 access는 다음 요청부터 거부된다. tokenVersion은 없앤다.
6. 만료된 세션 행은 매일 정리 작업이 지운다.

## 고려한 대안
| 대안 | 얻는 것 | 고르지 않은 이유 |
|---|---|---|
| ADR-006 유지(Redis tokenVersion + Redis 세션) | 이미 있는 코드 | Redis 장애에 로그인한 요청이 모두 실패하고, 막으려면 장치가 셋 더 든다. 한 기기 로그아웃·재사용 탐지 뒤에도 access가 15분 통한다 |
| 무상태 JWT(요청마다 조회 없이 refresh 때만 확인) | 요청마다 조회가 없다 | 비밀번호 변경·제재가 access 만료(15분)까지 반영되지 않는다 |
| 세션 토큰 하나(무작위 문자열, 회전 없음) | 토큰이 하나라 단순하다 | 재사용 탐지가 없어, 탈취된 토큰은 쓰이는 한 만료되지 않는다 |
| 세션 토큰 하나 + 연장할 때 회전 | 토큰 하나로 재사용 탐지 | 회전 순간 출발한 요청 때문에 직전 해시와 유예 시간을 저장해야 하고, 새 토큰을 응답 헤더로 내려 프론트가 바꿔 끼워야 한다 |
| 세션을 Redis에만 둔다 | 키 만료가 세션 만료를 맡아 정리 작업이 없고, 요청마다의 조회가 DB와 커넥션 풀(31)을 쓰지 않는다 | Redis가 멈추면 로그인한 요청이 모두 실패한다. 회원 상태·역할은 DB에 있어 요청마다 확인하려면 결국 DB를 읽거나 세션에 복사해 맞춰야 한다 |
| DB 세션 + Redis 캐시 | 요청마다의 조회가 대부분 Redis에서 끝난다 | 세션을 지운 뒤 캐시 삭제가 실패하거나 동시에 들어온 요청이 옛 값을 다시 채우면 지운 세션이 캐시에 남아 통과한다. [SUB-16](../perf/sub-16-s04-auth.md)에서 재 보니 보통 부하에서 DB 세션의 인증 비용이 p95 약 1ms라 줄일 것이 거의 없다 |
| 절대 만료(로그인 뒤 30일) | 탈취된 refresh의 최대 수명이 정해진다 | 계속 쓰는 사용자도 주기적으로 다시 로그인한다. 탈취는 재사용 탐지와 비밀번호 변경·전체 로그아웃으로 막는다 |

## 결과
- 로그인한 요청마다 DB 조회 1번(세션 기본키와 회원 조인)이 생기고 커넥션 풀(31)의 연결을 잠깐 쓴다. Redis 조회는 없어진다. [SUB-16 S-04](../perf/sub-16-s04-auth.md)에서 인증 비용(토큰 있음과 없음의 p95 차이)은 보통 부하(30 VU)에서 1.1ms로 요구사항(NFR-PERF-04, 10ms 미만)을 채웠다. VM CPU 한계 근처(100 VU)에서는 12~14ms로 늘었는데(바꾸기 전 Redis 조회는 약 4ms), 커넥션 풀 대기는 없었고 요청당 postgres CPU 약 0.07ms가 한계 근처의 대기열을 늘린 것이다. 그래서 세션 캐시는 CPU 한계보다 아래의 부하에서 p95 차이가 10ms를 넘거나 커넥션 풀 대기가 생길 때 실험한다.
- Redis 장애는 로그인한 요청, 갱신, 로그아웃·비밀번호 변경·제재·탈퇴에 영향을 주지 않는다. Redis는 로그인 실패 횟수, 이메일 인증 코드, 가입 인증·소셜 가입 토큰에만 남는다.
- 한 기기 로그아웃과 재사용 탐지가 그 기기의 access까지 바로 끊고, 역할 변경이 다음 요청부터 반영된다.
- API와 응답 모양, 프론트 흐름은 그대로다. `member.token_version` 컬럼은 롤백할 수 있게 남겼다가 다음 배포(`V202611251814__member_drop_token_version.sql`)에서 지웠다([ADR-011](ADR-011-ops-practice-environment.md) 결정 7). 배포하면 Redis의 refresh 세션을 읽지 않으므로 사용자가 한 번 다시 로그인한다.
- 요청마다 저장소를 보므로 access 검증은 무상태가 아니다. JWT는 세션을 가리키는 `sid`와 만료를 위조할 수 없게 담아, access를 저장하지 않고도 만료까지 유효하게 두는 데 쓴다.

## 면접 연결
- "매 요청 DB를 볼 거면 왜 JWT인가요?" → 맥락의 넷째·다섯째 항목: 둘로 나눈 이유는 재사용 탐지이고, access를 JWT로 둔 이유는 저장하지 않고도 짧은 만료를 위조할 수 없게 담기 위해서다. JWT가 꼭 필요한 건 아니고 서명된 짧은 수명 토큰이 필요했다
- "JWT는 언제 쓰나요?" → 발급자와 검증자가 다르고(OIDC ID 토큰, 외부 인증 서버, 서비스 간 신원) 검증자가 묻지 않고 서명만으로 받아들일 때. 이 앱은 그 용도가 아니라 세션을 가리키는 토큰으로 쓴다
- "로그아웃하면 access는요?" → 세션 행을 지우면 그 `sid`의 access가 다음 요청부터 거부된다
