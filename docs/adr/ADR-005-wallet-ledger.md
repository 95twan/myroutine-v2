# ADR-005. 예치금은 단일 원장(ledger) + 잔액 스냅샷 + 보류(hold)로 모델링한다

- 상태: **폐기** (2026-10-02) — 사용자 결정으로 예치금(지갑) 기능 전체를 제거했다. 결제는 Toss 단일 수단, 환불은 PG 부분취소, 정산금은 지급 Mock(`PayoutGateway`)으로 대체한다([요구사항 POL-01·08·12](../01-requirements/README.md)).
  - 폐기로 잃는 것: 예치금 동시 차감·원장 대조라는 동시성·정합성 사례. 남는 사례: 재고 예약(1-9), 결제 CAS·대사(2-4·2-6), 품목 환불의 누적 취소 한도(2-8), 정산 1회(3-4).
  - 이 ADR의 교훈 중 "외부 송금은 트랜잭션 밖에서, 멱등 키로"는 정산 지급([ADR-009](ADR-009-settlement.md))에 그대로 적용한다.
- (원래 상태: 승인 2026-10-02)
- 관련: [03-erd.md wallet](../02-design/03-erd.md), INV-05·06

## 맥락
- As-Is: `wallet.balance`를 직접 증감하고, 로그는 용도별 4개 테이블에 흩어져 있었다(WAL-05). 잔액이 기록 합계와 맞는지 검증할 수 없었다.
- 출금이 멱등하지 않았고(WAL-01), 송금 시 DB 락을 잡은 채 외부를 호출했다(WAL-02).
- v2는 복합결제라서 "결제 진행 중인 금액"을 잡아둘 수단이 필요하다.

## 결정
1. 모든 증감은 `ledger_entry` 한 테이블에 부호 있는 금액으로 기록한다. `wallet.balance`는 원장 합계의 스냅샷이다.
2. 원장에 `UK(type, ref_type, ref_id)`를 둔다. 같은 충전·환불·정산·결제가 두 번 반영되지 않고, 중복 요청에는 기존 결과를 돌려준다.
3. 잔액 변경은 지갑 행을 `SELECT ... FOR UPDATE`로 잠근 뒤 원장 INSERT + 잔액 UPDATE를 한 트랜잭션에서 한다.
4. **보류**: `wallet.held`와 `wallet_hold(order_id UK)`. 가용잔액 = balance - held. 확정 시 원장 `ORDER_PAYMENT` 기록 + balance·held 차감, 해제 시 held만 차감.
5. **외부 송금(출금)은 차감을 먼저 커밋하고 트랜잭션 밖에서 호출**한다. 실패하면 `WITHDRAWAL_REVERT`로 복원하고, 불확실하면 조회로 확정한다.
6. 정합성 점검 잡이 `balance = Σ ledger`, `held = Σ HELD hold`를 매일 검증해 불일치를 메트릭으로 남긴다.

## 고려한 대안
| 대안 | 기각 이유 |
|---|---|
| 잔액 없이 원장 합계만 (매번 SUM) | 조회 비용이 원장 크기에 비례. 동시 차감 시 음수 방지가 어려움 |
| 낙관적 락(version) | 주문 결제·환불이 같은 지갑에 몰리는 경우는 드물지만, 충돌 시 재시도 로직이 모든 호출자에 퍼짐. 지갑 단위 비관적 락이 단순하고 경합도 낮음 |
| 복식부기(차변·대변 계정) | 회계 정확성은 높지만 범위 대비 과함. 단식 원장 + 참조로 감사 추적 요구는 충족 |
| 보류를 주문 쪽에서 관리 | 가용잔액 계산이 두 모듈에 걸쳐 원자성을 잃음 |

## 결과
- INV-05를 DB 제약(잔액 ≥ 0 CHECK, held ≤ balance CHECK) + 원장 unique + 점검 잡으로 보장한다.
- 원장은 가장 빨리 커지는 테이블 중 하나 → Stage 2-7 월 파티셔닝 후보.
- 동시성 테스트: 같은 지갑에 동시 보류·환불·정산 입금 → 잔액 = 원장 합계, 음수 0건.

## 면접 연결
- "포인트(예치금) 동시 차감은 어떻게 막았나요?" → 지갑 행 락 + CHECK 제약 + 원장 unique
- "잔액이 틀어지면 어떻게 아나요?" → 원장 대조 점검 잡
- "외부 송금 중 장애가 나면?" → 선차감 커밋 → 호출 → 확정/복원
