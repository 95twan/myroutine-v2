## 5-1. 빌링키 등록 · 조회 · 삭제 (M)

**목표**: 카드를 빌링키로 등록해 두고 구독 결제에 쓴다.

**새로 등장**: Toss 빌링(자동결제) — 카드 인증으로 받은 authKey를 서버가 빌링키로 바꾸고, 이후 빌링키로 결제를 요청한다.

**할 일**
1. `billing_key` 마이그레이션(빌링키 암호화 저장, 카드 요약만 노출)
2. `TossClient`에 빌링키 발급·빌링 승인 추가(결과 3분류 그대로)
3. `POST /api/billing-keys`, 조회, 삭제(활성 구독이 쓰면 409, OPEN-04)
4. `member-withdrawn` consumer → 빌링키 삭제

**완료 확인**
- [ ] 발급 성공·실패, 빌링 승인 3분류 (가짜 PG 서버)
- [ ] 응답·로그에 빌링키 원문이 없다

**리뷰 때 물어볼 것**: 암호화 키는 어디서 관리하나?

## 5-2. 구독 신청 · 관리 (M)

**목표**: 구독 신청(수량, 매주 N요일 / 매월 N일, 배송지, 빌링키), 조회·수정·일시정지·재개·해지. **본인 구독만** 다룰 수 있다.

**할 일**
1. `subscription` 마이그레이션, `Subscription` 애그리거트(다음 실행일 계산, 상태 전이 = [상태머신 §8](../02-design/04-state-machines.md))
2. 구독 가능 상품만, 자기 가게 상품 불가, 신청 시점 가격 저장
3. 모든 조회·변경은 `findByIdAndMemberId` (As-Is ORD-08 IDOR 재발 방지)
4. 가게 폐업·탈퇴 조건(3-2, 3-6)에 "활성 구독" 조건 추가

**완료 확인**
- [ ] 다음 실행일 계산: 요일·일자 경계, 월말, 2월, 재개 시 재계산 (단위 테스트)
- [ ] 다른 회원 구독 조회·일시정지·해지 → 404
- [ ] 상태 전이 허용·금지 전체

**리뷰 때 물어볼 것**: 날짜 계산을 어디에 두었나? 매월 29~31일을 막은 이유는?

## 5-3. 구독 회차 실행 잡 (L)

**목표**: 매일 06:00 실행일이 된 구독마다 주문을 만들고 빌링키로 결제한다. 실패하면 다음 날 재시도, 3회 연속 실패하면 일시정지(SUSPENDED). 재고가 없으면 건너뛴다.

**새로 등장**: 회차 멱등 — `subscription_cycle(subscription_id, run_date)` unique + CAS 선점으로 같은 회차를 두 번 처리하지 않는다.

**할 일**
1. `subscription_cycle` 마이그레이션
2. 잡(잡 락, keyset 순회, 구독별 처리): 회차 선점 → 적용가 결정 → 체크아웃 로직 재사용해 주문 생성(멱등키 `cycleId:attempt`) → 빌링 결제 → 결과 반영
3. 결과 불확실 → 주문은 PAYMENT_IN_PROGRESS, 2-8 주문 대사가 이어서 처리
4. [시퀀스 §5](../02-design/06-sequences.md)

**완료 확인**
- [ ] 정상 회차 → 주문 1건 PAID, 다음 실행일 갱신
- [ ] **같은 날 잡 두 번 → 주문 1건** (INV-08)
- [ ] 3회 연속 실패 → SUSPENDED + 이벤트, 2회 실패 후 성공 → 실패 횟수 0
- [ ] 재고 부족 → SKIPPED, 실패 횟수 그대로

**리뷰 때 물어볼 것**: 구독 결제가 중복으로 나가지 않게 어떻게 했나? 체크아웃 코드를 어떻게 재사용했나?

## 5-4. 가격 변경 · 종료 이벤트 반영 (M)

**목표**: 상품 가격이 오르면 구독자에게 알리고 유예 후 적용, 내리면 바로 적용(OPEN-05). 상품 단종·가게 폐업·회원 탈퇴 시 구독 종료.

**할 일**
1. `product-price-changed` consumer: 인상이면 `pending_unit_price`와 적용일(다음 회차가 3일 이내면 그다음 회차), 인하면 바로 반영 + 알림 이벤트
2. `product-discontinued`, `shop-closed`, `member-withdrawn` consumer → TERMINATED(멱등)
3. 이벤트 version으로 늦게 도착한 오래된 가격 이벤트를 무시
4. `GET /api/shops/{shopId}/subscriptions` (판매자 구독 현황)

**완료 확인**
- [ ] 다음 회차 2일 전 인상 → 그 회차는 기존가, 다음 회차부터 인상가
- [ ] 가격 이벤트 순서가 뒤바뀌어도 최신 가격 유지
- [ ] 단종 이벤트 두 번 → 종료 1번

**리뷰 때 물어볼 것**: 이벤트 순서가 바뀌면 어떻게 되나?
