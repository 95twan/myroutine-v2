# SUB-16 S-04 인증 비용 리포트

## 무엇을 했나

[SUB-25](../04-sub/session-auth.md)에서 세션을 Redis에서 DB로 옮긴 뒤, 요청마다 하는 인증이 얼마나 드는지를 바꾸기 전과 같은 VM, 같은 데이터에서 쟀다. 결과로 세션 앞에 Redis 캐시를 둘지 정했다([ADR-015](../adr/ADR-015-session-auth.md)).

| 앱 | 요청마다 인증이 하는 일 | 코드 |
|---|---|---|
| Redis 토큰 버전 (SUB-24) | JWT 서명 검증 + Redis `auth:token-version` GET 1번 | `d1d9519` |
| DB 세션 (SUB-25) | JWT 서명 검증 + `member.auth_session`과 `member.member` 조인 조회 1번 | `af9df61` |

두 커밋은 인증 말고는 코드가 같다. 지금 운영 VM에 `workflow_dispatch`로 차례로 배포해 쟀다.

## 측정 조건

VM 1대(vCPU 8)에 앱 1개와 모든 서비스가 함께 떠 있고, k6는 같은 네트워크의 개발 PC에서 보냈다. 공개 API `GET /api/products/{id}`를 대기 없이 계속 보내고(1분 램프업 뒤 5분 유지), 토큰 없이 한 번, 토큰을 붙여 한 번 재서 그 차이를 인증 비용으로 봤다. 상품 조회 비용은 양쪽에 똑같이 들어가 차이에서 빠진다. 토큰은 k6 회원 100명으로 로그인해 VU마다 하나씩 썼다.

- 앱마다 배포 직후 토큰 없음과 있음으로 30초씩 데운 뒤, 없음 → 있음을 두 번(DB 세션은 세 번) 쟀다.
- k6 요약은 전체 요청 기준이라, 토큰 있음에는 준비 단계의 로그인과 확인 요청 200건이 섞여 있다. 회당 140만 건 이상 중 200건이라 p95에는 영향이 없다.
- 인증 비용은 두 분포의 p95 차이이지, 요청 하나하나가 더 걸린 시간의 p95는 아니다.

## 발견

### 보통 부하에서 DB 세션의 인증 비용은 p95 약 1ms다

30 VU(초당 약 3,700건)에서 토큰 있음과 없음의 p95 차이는 1.1ms, 중앙값 차이는 0.6ms였다. 요구사항(NFR-PERF-04, p95 차이 10ms 미만)을 넉넉히 채운다. 이 부하도 100 VU 처리량의 약 70%라 가벼운 부하가 아니다.

### 늘어난 꼬리는 CPU 한계 근처에서 생긴 대기였다

100 VU에서는 DB 세션의 p95 차이가 12~14ms로 기준을 넘었고, Redis 토큰 버전은 약 4ms였다. 그런데 중앙값 차이는 DB 세션이 약 1.5ms로 오히려 작았다. 보통의 요청은 거의 차이가 없고, 느린 쪽 일부만 늘어난 것이다.

이때 VM의 컨테이너들은 8코어 중 약 6.6~6.9코어를 썼다. 커널과 네트워크 처리까지 더하면 한계 가까이다. 세션 조회는 요청당 CPU를 약 0.07ms(postgres) 더 쓰고, 한계 근처에서 이 일이 더해진 만큼 대기열이 길어져 꼬리로 드러났다. 커넥션 풀 대기는 없었으므로 풀이 원인은 아니다. 부하를 30 VU로 낮추자 차이가 1.1ms로 줄어 이 해석과 맞았다.

DB 세션 1·2회는 토큰 없음도 느렸고(p99 약 106ms) CPU를 덜 쓰고도 처리량이 낮았다(약 5.8코어). VM 안이 아니라 같은 호스트의 다른 부하 같은 바깥 조건으로 보고, 토큰 없음이 Redis 토큰 버전과 같았던 3회를 가장 깨끗한 비교로 봤다.

### 캐시는 더하지 않는다

캐시가 맞는 요청은 Redis GET 1번이라 Redis 토큰 버전과 같은 모양이고, 그래서 캐시로 얻을 수 있는 몫은 CPU 한계 근처의 p95 약 9ms(13.5ms → 약 4ms)가 상한이다. 보통 부하에서는 줄일 것이 1ms 남짓이다. 반면 캐시를 두면 세션을 지운 뒤 캐시에 남은 세션이 통과하는 문제와, Redis가 멈출 때 요청마다 타임아웃을 기다리지 않게 하는 장치가 다시 필요하다. 그래서 캐시를 실험하는 조건을 "CPU 한계보다 아래의 부하에서 p95 차이가 10ms를 넘거나, 커넥션 풀 대기가 생길 때"로 고치고, 지금은 더하지 않는다. 한계 근처의 꼬리는 [알려진 문제](../known-issues.md)에 남겼다.

## 다음에 할 일

- Redis 토큰 버전을 30 VU로는 재지 않았다. 보통 부하에서 두 방식의 차이는 DB 세션의 1.1ms 이하로만 말할 수 있다.
- 운영 부하가 VM CPU 한계에 가까워지거나 커넥션 풀 대기가 생기면, 세션 캐시를 실험 브랜치로 구현해 이 측정과 같은 조건으로 잰다.
