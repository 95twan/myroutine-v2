# S2-5 재고 차감 방식 비교 리포트

## 무엇을 했나

재고 예약을 세 방식으로 구현해 같은 VM, 같은 데이터, 같은 커넥션 풀(31)에서 쟀다.

| 방식 | 재고 행을 다루는 법 | 코드 |
|---|---|---|
| A. 조건부 UPDATE (지금) | `UPDATE ... SET available = available - :q ... WHERE available >= :q` 한 문장 | `d0ab28f` |
| B. JPA 비관적 락 | `@Lock(PESSIMISTIC_WRITE)` 조회(`SELECT ... FOR UPDATE`)로 읽고, 엔티티 메서드로 확인·차감 | `6f25f87` |
| C. Redis 선착순 게이트 | Lua 스크립트로 Redis 수량을 먼저 확인·차감하고, 통과한 요청만 A의 UPDATE | `c743d21` |

B와 C는 머지하지 않는 실험 브랜치에 두었다. [Baseline](s2-1a-baseline.md)의 인기 상품 측정은 응답 대부분이 커넥션 10개를 기다린 시간이라 재고 행 락이 가려졌다. [S2-3](s2-3-pool-scheduling.md)에서 풀을 31로 늘렸으므로, 지금 방식(A)도 다시 재서 기준으로 썼다.

## 측정 조건

VM 1대(vCPU 8, RAM 16GB)에 앱 1개와 모든 서비스가 함께 떠 있다. 데이터는 시드 스냅샷 `seed_s2-3`(주문 1,000만 건)이고, 측정마다 새 인기 상품을 만들어 시드 회원의 장바구니를 그 상품으로 옮겼다. 결제 TTL을 180분으로 늘려 측정 중에는 주문 만료와 재고 복구가 일어나지 않게 했다.

| 측정 | 부하 |
|---|---|
| 몰림 | 재고 100개 상품을 회원 1,000명이 동시에 한 번씩 주문한다 |
| 지속 경합 | 재고 100만 개 상품을 회원 100명이 3분 동안 쉬지 않고 반복 주문한다. 모두 성공한다 |

방식마다 3번씩, A·B·C → B·C·A → C·A·B 순서로 돌렸다. A의 3회 몰림(A3)은 1,000건 중 51건이 앱에 닿기 전에 연결 단계에서 끊겨(연결 재설정 24건, 60초 시간 초과 27건) 949건만 경합했다. 그래서 9칸이 끝난 뒤 A 몰림을 한 번 더 재서(A4) A3 대신 썼다. 51건의 실패는 체크아웃 처리 전에 일어난 것이라 재고 방식과는 관계없다.

## 결과

모든 측정에서 초과 판매는 없었다. 몰림 10번 모두 정확히 100건 성공, 판매 가능 0, 예약 100이었고, C는 Redis 값도 0이었다. 지속 경합 9번 모두 예약 수량, 예약 레코드 수, k6 성공 수가 같았고, C는 Redis 값이 DB의 판매 가능 수량과 같았다.

### 몰림

| 방식 | p50 | p95 | 최대 | 재고 문장 호출 | 재고 문장 평균 |
|---|---|---|---|---|---|
| A | 719\~872ms | 907\~1,162ms | 1,069\~1,313ms | 1,000회 | 11.6\~13.7ms |
| B | 755\~945ms | 985\~1,212ms | 1,117\~1,294ms | 1,000회 | 21.8\~25.9ms |
| C | 703\~782ms | 896\~921ms | 963\~1,031ms | 100회 | 108\~127ms |

재고 문장은 A·C의 조건부 UPDATE, B의 `SELECT ... FOR UPDATE`다. 행 락을 기다린 시간은 이 문장의 실행 시간에 들어간다.

| 회차별 p95 | 1회 | 2회 | 3회 |
|---|---|---|---|
| A | 1,162ms | 907ms | 1,064ms (A4) |
| B | 1,212ms | 1,030ms | 985ms |
| C | 921ms | 902ms | 896ms |

|---|---|---|---|---|---|
| A | 268 / 292 / 293 | 312\~340ms | 628\~686ms | 809\~892ms | 1.4\~1.5초 |
| B | 261 / 277 / 279 | 274\~291ms | 892\~960ms | 1,435\~1,560ms | 3.5\~5.0초 |

| 방식 | 재고 문장 평균 | 사용 중 커넥션 | 행 락을 기다리는 연결 | CPU (앱 / postgres) |

지표는 측정 중 2분 평균이다. 재고 문장이 DB 실행 시간의 약 99%를 썼다.

## 발견

### 세 방식 모두 재고 행 하나에서 초당 약 290건이 한계였다

지속 경합에서 세 방식 모두 초당 약 290건에서 멈췄다. 커넥션 31개 중 약 30개가 사용 중이었고, 그중 약 20\~26개가 재고 행 락을 기다렸다. CPU는 앱과 postgres 모두 1코어도 쓰지 않았다. 같은 행을 고치는 트랜잭션은 한 번에 하나씩만 지나가므로, 한 트랜잭션이 락을 쥐는 시간(약 3.4ms = 1초 ÷ 290)이 처리량을 정한다. 이 시간에는 예약·이력 INSERT와 커밋의 디스크 쓰기가 들어 있다.

C도 여기서는 A와 같았다. 재고가 넉넉하면 거를 요청이 없어서, 모두가 Redis를 거친 뒤 같은 재고 행 앞에 다시 줄을 선다.

다음 단계: 이 한계를 넘으려면 재고 행을 여러 개로 나누거나 DB 차감을 나중으로 미뤄야 한다. 체크아웃 흐름과 재고 보정 설계가 바뀌어 이번에는 하지 않는다.

### JPA 비관적 락(B)은 처리량은 같고 응답 꼬리가 길었다

지속 경합에서 B의 처리량(초당 261\~279건)은 A(268\~293건)와 범위가 겹쳤다. 하지만 p95는 892\~960ms로 A의 628\~686ms보다 세 번 모두 높았고, p99와 최대는 A의 2\~3배였다. A·C에서 락을 기다리는 연결은 대부분 `transactionid`를, B에서는 `tuple`을 기다렸다. 같은 행을 기다려도 `SELECT ... FOR UPDATE`와 UPDATE가 줄을 서는 방식이 다르다는 것은 보이지만, 그 차이가 왜 긴 꼬리로 이어지는지는 이번 측정으로 가리지 못했다.

몰림에서는 거절될 900건도 B에서는 락을 잡았다. 그래서 재고 문장의 평균이 A의 약 2배(21.8\~25.9ms 대 11.6\~13.7ms)였다. 응답 p95는 A와 범위가 겹쳤다.

다음 단계: 없음. B를 쓸 이유가 나오지 않았다.

### Redis 게이트(C)는 거절을 DB 앞에서 끝냈지만, 응답 차이는 흔들림 안이었다

몰림에서 C는 900건을 Redis에서 거절해 DB의 재고 UPDATE가 100번만 돌았다(A는 1,000번). p95는 896\~921ms로 세 번 모두 가장 낮고 고르게 나왔다. 하지만 A의 범위(907\~1,162ms)와 겹친다.

A에서 거절된 요청이 재고 행에서 기다린 시간은 평균 약 12ms다. 응답 p50이 700\~870ms인 것에 비하면 작다. 1,000건이 동시에 커넥션 31개를 나눠 쓰는 대기와 체크아웃의 나머지 처리가 응답 대부분이라, 거절을 DB 앞에서 끝내도 응답이 크게 줄지 않았다.

C를 운영에 넣으려면 재고가 바뀌는 모든 곳(상품 등록, 판매자 재고 변경, 결제 대기 만료, 주문 취소·반품 복구)에서 Redis도 같이 바꿔야 하고, 키가 없거나 Redis가 멈췄을 때 다시 맞추는 방법이 필요하다. 이번 측정에서 얻는 이득은 이 비용을 정당화하지 못한다.

다음 단계: 없음.

### 지금 방식(A)을 유지한다

| 방식 | 정확성 | 지속 경합 | 몰림 | 운영 비용 |
|---|---|---|---|---|
| A | 초과 판매 0 | 초당 약 290건, p95 약 650ms | p95 0.9\~1.2초 | 문장 하나 |
| B | 초과 판매 0 | 처리량 같음, p95 +약 270ms, 꼬리 2\~3배 | A와 범위 겹침, 재고 문장 2배 | 엔티티 메서드 하나 |
| C | 초과 판매 0 | A와 같음 | 가장 낮고 고르나 A와 범위 겹침, DB 재고 문장 1/10 | Redis와 DB를 맞추는 코드 전부 |

세 방식 모두 초과 판매가 없었고, 처리량은 재고 행 하나가 정했다. B는 꼬리가 길어졌고, C는 DB 일을 줄였지만 응답으로 드러나는 이득이 흔들림 안이었으며 Redis와 DB를 맞추는 비용이 크다. 그래서 문장 하나로 확인과 차감을 끝내는 A를 그대로 쓴다([ADR-008](../adr/ADR-008-inventory-reservation.md)).

### 풀을 31로 늘리자 기다림이 커넥션 앞에서 재고 행 락으로 옮겨 갔다

Baseline(풀 10)의 몰림은 p95 2.70초였고 재고 UPDATE 평균은 3.87ms였다. 풀 31에서 A는 p95 0.9\~1.2초, 재고 UPDATE 평균 11.6\~13.7ms다. 커넥션을 기다리던 요청이 DB 안까지 들어와 재고 행 앞에서 기다리게 된 것이다. 이번 비교가 의미 있었던 것도 이 때문이다.

다음 단계: 없음.

## 측정하면서 바로잡은 것

- B는 처음에 `SELECT available ... FOR UPDATE`로 읽은 뒤 A의 조건부 UPDATE를 다시 부르는 형태로 정했다. A와 UPDATE를 같게 두려는 것이었지만 실제로 쓰지 않는 코드라, 실무에서 말하는 JPA 비관적 락(엔티티를 잠그며 읽고 메서드로 차감)으로 바꿨다.
- A3 몰림의 연결 실패 51건 때문에 A 몰림을 9칸이 끝난 뒤 한 번 더 쟀다(A4). A4만 순환 순서 밖에서 쟀다.
- 몰림의 1회차가 세 방식 모두 가장 느렸다(p95 A 1,162ms, B 1,212ms, C 921ms). 순서를 돌려 쟀으므로 한 방식에만 걸린 것은 아니다.
